## 1. PROJECT IDENTITY

**Project name:** ARGUS Security Intelligence Workspace
**Project purpose:** Real-time Windows Endpoint Detection and Response (EDR) and Security Operations Center (SOC) dashboard.
**Current state:** Beta / Advanced Production Candidate
**Workspace structure:** pnpm Monorepo Workspaces (`@workspace/*`)
**Package manager:** pnpm (v10)
**Programming languages:** TypeScript (Frontend/API), Python 3.10+ (Sensor)
**Frameworks:** React 19, Vite, Tailwind CSS, Framer Motion, Three.js / React Three Fiber, Express 5.
**Build tools:** esbuild (backend), Vite (frontend), PyInstaller (sensor), Inno Setup (installer).
**Desktop technology:** Custom standalone executable bundler packaging Node.js, the React static assets, and the Python agent into `ARGUS-Setup.exe`.
**Backend architecture:** Node.js Express REST API + Server-Sent Events (SSE) `EventHub`.
**Frontend architecture:** Single Page Application (SPA) driven by real-time streams.
**Security engine architecture:** Python 3 daemon leveraging `psutil`, native Win32 sockets, and polling loops. Supervisor-managed (`agent_supervisor.py`).
**Database technology:** Drizzle ORM + PostgreSQL schema defined, but the application currently operates entirely in-memory (volatile EventHub).
**External services:** None (Local-first architecture).

**Architecture in Plain English:**
ARGUS operates on a hub-and-spoke model running locally on a Windows host. A native Python security agent (`security-engine`) acts as the sensor, continuously polling the operating system for running processes, network sockets, active ports, and filesystem changes. The agent pushes this telemetry via HTTP POST to a local Node.js API server running on port 5000. The API server evaluates this data against a deterministic rule engine (48+ rules), stores it in an in-memory `EventHub`, and broadcasts it via Server-Sent Events (SSE). A React-based web dashboard (running on port 5173 or served statically via the API server) consumes the SSE stream to render an interactive, real-time SOC interface.

## 3. CURRENT ARGUS ARCHITECTURE

**Data Flow Trace:**
`Windows OS (psutil/Win32 APIs)` → `Python Security Engine (Polling)` → `HTTP POST` → `Local API Server (Express)` → `In-Memory EventHub` → `Rule Engine Evaluation` → `Alert Generation` → `SSE Broadcast` → `React Frontend` → `User Action (API POST)` → `Local API Server (Remediation Route)` → `System Execution (taskkill)`

**Component Details:**
1. **Security Engine (Sensor):**
   * *Technology:* Python 3 (`psutil`, `requests`).
   * *Responsibility:* Gather raw telemetry (Process, Network, Topology, Ports, Files, Peripherals).
   * *Communication:* Synchronous HTTP POST to API Server (`/api/events/*`).
   * *Limitations:* Relies on user-mode polling (every 1-15 seconds). It can miss sub-second process execution (e.g., rapid script drops).
2. **API Server (Event Broker & Engine):**
   * *Technology:* Node.js, Express 5.
   * *Responsibility:* Receive telemetry, evaluate rules, proxy data to UI.
   * *Communication:* Synchronous REST (Ingest/Remediation), Asynchronous SSE (Broadcast).
   * *Limitations:* In-memory EventHub limits historical retention. Node.js single thread could bottleneck under massive telemetry floods.
3. **Frontend (SOC Dashboard):**
   * *Technology:* React 19.
   * *Responsibility:* Visualization, threat analysis, interactive graphs.
   * *Communication:* Asynchronous SSE (`/api/telemetry/stream`), REST API (actions).
   * *Limitations:* Browser memory limits the size of the renderable process tree.

## 5. BACKEND/API AUDIT

* **Server Entry Point:** `artifacts/api-server/src/index.ts` (Bootstrap) -> `app.ts` (Express stack).
* **Event System / SSE:** `EventHub` class utilizing Node's `EventEmitter` to push JSON stringified payloads to long-polling HTTP connections.
* **Authentication:** Validates an Access Key, sets an HMAC signed `argus_activation` HttpOnly cookie.

**API Inventory (Key Endpoints):**
* `POST /api/auth/activate` | Authenticate | NO AUTH | IMPLEMENTED
* `GET /api/auth/status` | Check Session | YES | IMPLEMENTED
* `GET /api/system/telemetry/stream` | Stream Vitals | YES | IMPLEMENTED
* `POST /api/events/process` | Ingest Telemetry | NO AUTH (Sensor) | IMPLEMENTED
* `GET /api/processes` | List Processes | YES | IMPLEMENTED
* `POST /api/processes/:pid/terminate` | Kill Process | YES | IMPLEMENTED (Executes `taskkill /F /T`)
* `POST /api/recovery/quarantine` | Isolate File | YES | PARTIAL

**Security Concerns in API:**
* `POST /api/processes/:pid/terminate` validates PID to prevent killing `0` and `4`, but executing shell commands (`taskkill`) based on user input carries inherent command injection risks if validation logic is ever loosened.
* No internal authentication between the Python sensor and the API Server. Any local process can POST to `/api/events/*` and spoof telemetry.

## 7. DETECTION ENGINE AUDIT

* **Location:** `artifacts/api-server/src/detection/`
* **Count:** 48+ Deterministic Rules (`PROC-001..`, `NET-001..`, `FILE-001..`).
* **Logic:** Synchronous evaluation pipeline. Incoming JSON events are parsed through Zod schemas, then passed through rule filters.
* **Severity Calculation:** Hardcoded per rule (`CRITICAL`, `HIGH`, `MEDIUM`).
* **Correlation:** Partial. Process ancestry is stitched together for the UI via `useThreatAnalysis`, but the backend rule engine evaluates events largely in isolation (stateless detection). No complex MITRE ATT&CK temporal chaining (e.g., Event A + Event B within 5 mins = Alert).

## 8. THREAT MODEL

**Implemented Detects:**
* PowerShell/CMD abuse (LOLBins).
* Masquerading (e.g., `svchost.exe` running from `C:\Temp`).
* Suspicious staging directories (`AppData`, `Downloads`).
* High resource utilization anomalies (Cryptojacking).
* Peripheral (Camera/Mic) snooping.
* Wildcard port bindings (`0.0.0.0` listeners).

**Missing / Blind Spots:**
* Privilege Escalation / Token Manipulation.
* Lateral Movement (Pass-the-Hash).
* Memory Injection / Process Hollowing / DLL Hijacking.
* Kernel Rootkits.

## 10. AUTHENTICATION / ACTIVATION / LICENSING

* **Flow:** Enterprise "Access Key" model.
* **Mechanics:** User enters `ARGUS-DEV-2026`. Frontend POSTs to `/api/auth/activate`. Server validates logic. If valid, server attaches a secure `argus_activation` HttpOnly cookie with an HMAC signature and TTL.
* **Security:** Keys are NEVER stored in `localStorage` or `sessionStorage`. The UI asks the server (`/api/auth/status`) to verify identity. There are no user roles or multi-tenant abstractions; it is a single-tenant per-workstation architecture.

## 12. REAL-TIME EVENT PIPELINE

**Trace:**
Windows OS → Python `psutil` → HTTP `POST` → Express `/api/events/process` → Node.js `EventHub.addEvent()` → Rule Engine Evaluation → Node.js `EventEmitter` → HTTP SSE `/api/system/telemetry/stream` → React `useTelemetryStream` → DOM Render.

**Bottlenecks:**
1. *HTTP Overhead:* Creating a new HTTP POST request for every single process event is extremely inefficient compared to IPC, Pipes, or WebSockets.
2. *Memory Leaks:* Unbounded arrays in `EventHub` could crash the Node.js process after days of uptime if not strictly pruned.

## 13. DESKTOP READINESS AUDIT

* **Current Tech:** PyInstaller (for Python), esbuild (Node), Vite (React). Bundled via Inno Setup (`ARGUS-Setup.exe`).
* **Assessment:** PROTOTYPE-LEVEL.
* **Gaps:** It is essentially bundling web servers. To be a real Windows desktop app, it needs:
  * A true Windows Background Service implementation (so it runs before user login).
  * Secure IPC (Named Pipes) between the Python sensor and Node (or rewritten in Rust/C++).
  * Auto-update mechanics.
  * Self-defense mechanisms against `taskkill`.

---

## 14. KERNEL-LEVEL READINESS

* **CAN BE DONE IN USER MODE:** ETW (Event Tracing for Windows) consumption via Python/C#. This will instantly solve the "polling gap" and provide sub-second process execution telemetry without needing a kernel driver.
* **WOULD REQUIRE KERNEL/DRIVER SUPPORT:**
  * Proactive File/Process blocking (preventing execution *before* it happens).
  * Real-time filesystem Minifilter.
  * Self-defense (protecting ARGUS files/registry keys from Admin deletion).
* **Recommendation:** Integrate ETW first. It provides 80% of the visibility benefits of a driver with 0% of the blue-screen risks.

## 16. PERFORMANCE AUDIT

* **Bottlenecks:**
  1. `psutil` polling across hundreds of processes every 1 second causes persistent background CPU overhead.
  2. High-volume JSON serialization over HTTP loopback (Sensor -> API).
  3. React DOM rendering of 300+ nodes in the Process Graph (Framer Motion) can cause browser lag on low-end hardware.

* **Detection (7/10):** Strong deterministic rules, lacks behavioral ML.

---

## 22. CRITICAL GAPS (Top 5)

1. **[P0] Lack of Kernel Visibility:** User-space polling misses fileless malware and rapid execution.
2. **[P0] No Self-Defense:** The agent can be trivially killed by malware.
3. **[P1] Sensor-to-API Trust:** No authentication on the local loopback telemetry ingest.
4. **[P1] Memory Volatility:** `EventHub` will lose all forensic data on reboot. DB persistence must be activated.
5. **[P2] Response Limitations:** Quarantine and Network isolation are not physically enforced.

---

## 23. RECOMMENDED EVOLUTION

* **PHASE 1 (Harden Architecture):** Turn on the Drizzle PostgreSQL DB. Authenticate the Python-to-Node loopback.
* **PHASE 2 (Advanced Telemetry):** Replace Python `psutil` process polling with Python ETW (Event Tracing for Windows) consumption to catch sub-second execution.
* **PHASE 3 (Local Intelligence):** Connect the existing SSE stream to a local Ollama instance for autonomous alert summarization.
* **PHASE 4 (Kernel Transition):** Write a C++ Windows Minifilter driver for file interception and self-defense, deprecating the Python filesystem watcher.

---

## 24. FINAL EXECUTIVE REPORT

**ARGUS CURRENT STATE:**
ARGUS is a beautifully engineered, highly functional EDR prototype. What is genuinely impressive is the real-time, low-latency SSE pipeline pushing native Windows telemetry directly into a world-class React dashboard. The deterministic rule engine works seamlessly.

What is currently weak is the reliance on user-space polling (`psutil`) and the lack of self-defense. To rival Microsoft Defender, ARGUS cannot rely on bundled Node/Python scripts running as standard executables.

**The Highest-Value Next Engineering Task:**
Transition the Python agent to consume **ETW (Event Tracing for Windows)**. This gives you near kernel-level visibility (catching rapid process injection and registry changes) without having to write C++ drivers immediately. Simultaneously, wire up the **Ollama Agent** to process the rich JSON telemetry you are already producing.
